# Plan: FedRAMP Drupal RAG Chatbot

**Date:** 2026-03-20  
**Status:** Draft

## Objective
Build a Drupal 10 module that adds a retrieval-augmented chatbot to dcpas.osd.mil, using only site content as its knowledge source and Azure OpenAI as the AI provider. The MVP should be FedRAMP-aligned, self-hosted for retrieval storage, and simple enough to demo while leaving a clear path to production hardening.

## Background
The target outcome is a Drupal 10 plugin/module that lets users ask questions and receive answers grounded in content from dcpas.osd.mil. The proposed architecture is a classic RAG flow:

1. Crawl and extract site content
2. Chunk content and generate embeddings
3. Store embeddings in a self-hosted vector index
4. At query time, retrieve relevant chunks
5. Send retrieved context plus user question to Azure OpenAI GPT-4 for response generation
6. Return an answer with citations

Key constraints and shaping decisions:

- **FedRAMP requirement:** deployed code must use **Azure OpenAI only** for AI services. No Anthropic dependencies, SDKs, or references in runtime code.
- **Storage requirement:** vector data must be self-hosted, with **SQLite or flat-file** storage rather than an external vector database.
- **MVP scope:** this is a demo-focused first version, so the plan should prioritize end-to-end functionality over advanced ranking or UI sophistication.
- **Drupal integration:** the frontend experience should be delivered as a Drupal 10 module, likely exposing:
  - a chat block/widget
  - an admin configuration form
  - backend routes/controllers/services for retrieval and answer generation
- **Engineering North Star:** implementation must use **Python stdlib only** for pipeline tooling, place shared logic in `lib/`, avoid “god scripts,” and ship documentation updates in every sprint.

Assumptions made to make this plan concrete:

- The ingestion/embedding pipeline is implemented as separate Python utilities for crawl/extract/chunk/embed/index tasks.
- The Drupal module consumes the resulting local retrieval store, either directly if co-located or via a simple file-based export format generated by the pipeline.
- Azure OpenAI API calls can be made from Drupal/PHP for chat completion, while Python tooling is used for ingestion/index generation.
- For the vector store, **SQLite** is the default choice because it provides queryable metadata and simpler operational handling than ad hoc flat files; cosine similarity can be computed in application code after fetching candidate vectors.

- [ ] Define the ingestion data model for documents, chunks, metadata, embeddings, and crawl status.
- [ ] Create a Python crawler script that fetches allowed pages from dcpas.osd.mil using stdlib HTTP tooling and respects configurable scope rules.
- [ ] Create a Python text-extraction script that converts crawled HTML into normalized text suitable for chunking.
- [ ] Create a Python chunking script that splits extracted text into retrieval-sized chunks with stable chunk IDs.
- [ ] Create a Python embedding script that sends chunk text to Azure OpenAI embeddings endpoints and stores returned vectors locally.
- [ ] Implement a self-hosted vector store in SQLite, including schema for chunks, source URLs, titles, embeddings, and timestamps.
- [ ] Implement a retrieval utility that can load stored embeddings and return top-K similar chunks for a test query.
- [ ] Add configuration handling for Azure endpoint, deployment name, API version, and API key without hardcoding secrets.
- [ ] Add a smoke-test script that runs one end-to-end indexing pass against a small page subset and verifies retrieval returns expected sources.
- [ ] Update `TOOLBOX.md` with pipeline commands and local usage instructions.
- [ ] Update `CLAUDE.md` with architectural decisions for ingestion, chunking, and vector storage.
- [ ] Update `AGENTS.md` with script responsibilities and boundaries.

## Design Decisions (Resolved)

1. **Vector store location:** SQLite co-located with Drupal on the same host. PHP module reads directly from MySQL (exported via `export_mysql.py`). For production scale, migrate to pgvector (Sprint 8).

2. **Content crawled:** Public HTML pages + PDFs from `TARGET_URL` (default: dcpas.osd.mil). Both supported in `run_pipeline.py`.

3. **Crawl boundaries:** Same-domain links only, configurable via `TARGET_URL` and `MAX_PAGES` env vars. Respects robots.txt via `crawler.py`.

4. **Secrets management (demo):** Environment variables via `.env` (ingestion) and `DCPAS_OPENAI_API_KEY` env var (Drupal). Full Azure Key Vault + `settings.php` injection path planned in Sprint 6.

5. **Model names:** Parameterized — `embedding_model` and `chat_model` config keys. Default: `text-embedding-3-small` + `gpt-4o`. For Azure: set to deployment names.

6. **Response latency:** Not formally measured yet. Sprint 6 adds response time logging. Top-K default of 5 is acceptable for demo.

7. **Citation fidelity:** Per-chunk source URL and title. Duplicate sources deduplicated in `PromptBuilder::extractCitations()`. Streaming not implemented in MVP (Sprint 3 deferred it).
